# Hackathon playbook: open-source contribution as your project

## Know the rules first
Ask the organisers: do contributions to existing projects count? Can the work start before the event? Judges usually reward a clear problem, a working result, and a good story, so plan for all three.

## Timeline (scale to 24h / 48h / 1 week)

| Phase | Share of time | What to do |
|---|---|---|
| Before the event | do it now | Interview, pick the org, install tools, fork, build, run the tests. Most lost hours are setup. |
| Pick and understand | 15% | Choose one small issue, read the repo tour, reproduce the bug. |
| Build | 40% | Failing test, smallest fix, run the project's checks. |
| PR and polish | 20% | Honest PR description, respond to CI, handle early review. |
| Demo prep | 25% | Before/after, tests, the PR link, what you learned. |

## What to demo (3 minutes)
1. The problem: show the bug live or a screenshot. (30 s)
2. How you found the cause: one architecture slide from the repo tour. (45 s)
3. The fix and the test: show the diff. (45 s)
4. The PR: link, CI status, reviewer feedback. (30 s)
5. What you learned and what is next. (30 s)

## Judges' likely questions
- Why this project? Who uses it?
- How did you pick the issue and know it was unclaimed?
- How did you test it?
- What would you do next? (Name a second issue.)

## Rules of thumb
- A merged one-line fix beats an unmerged ambitious one. Merging is up to maintainers, so frame the win as "PR opened, CI green, reviewed", not "merged".
- One PR per issue. Do not ask maintainers for quick reviews during the event.
- Keep a journal of dead ends. They make the best story.
